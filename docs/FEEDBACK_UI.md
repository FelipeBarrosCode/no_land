# Desktop feedback frontend / native handoff

Implementation is on `feat/feedback-program-desktop`. Frontend owns only `src/**`, the focused frontend test script, and this document. No provider operations or contributions are performed during implementation.

## Exact native seams

The frontend uses the commands and camelCase arguments in `IMPLEMENTATION_COORDINATION.md`, only through `invokeSafe`. There are no feedback HTTP requests, bearer tokens, deletion codes, or recovery proofs handled or persisted by JavaScript.

Native models inspected during implementation (`src-tauri/src/models/app_state.rs`, `models/feedback.rs`) expose **`machineId: string | null`** on offers/instances/provisioned rentals. This is not `providerMachineId` on the offer. The existing rented-instance summary does not need a machine field for review eligibility; that check is entirely native. Feedback summary JSON uses **`providerMachineId`**. Only positive canonical decimal strings within signed bigint range are accepted for machine joins. No host/offer fallback and no numeric machine-ID conversion. Existing numeric rental IDs are passed to feedback only if `Number.isSafeInteger` and positive; otherwise no review prompt.

`FeedbackProgramState` mirrors native version 1, including structured `pendingControlAction: {kind, requestId, expectedEpoch, enabled, optionalContextEnabled} | null`, enrollment recovery references, `receiptId`, `receiptStatus`, `receiptTokenRef`, and `collectionPaused`. These are references/metadata only. Unknown/malformed/future state fails closed. `feedback_program_status` must return the flattened state plus `configured`, `supported`, `statusMessage`, and `pendingSessions` and remain local-only. There is no new frontend state writer.

A native `feedback:invalidated` event is an optional acceleration signal (no payload trusted). It invalidates memory caches and refreshes local permission/status. Polling local status and hard 60-second read expiry also work without it. Emit it for accepted outcome/telemetry/review changes, deletion, moderation, and expiry if supported. Frontend independently invalidates on consent changes, read failures, report/block, and destruction completion.

## UI behavior

- Global top-left Feedback program entry on the main app, including onboarding/settings. Status is local-only on launch, focus, and every 30 seconds; no program API request while off unless the user explicitly opens/reloads enrollment information or chooses a control action.
- Enrollment/settings dialog: meaningful short disclosure, server-published policies/contact, separate unchecked required/optional consent, blank optional coarse profile, service/configuration/secure-store status, pending control and deletion receipt, stop, delete confirmation, and rejoin after pending controls resolve. No invented production URL/contact. Current published policy versions must match for rejoin because the consent command does not carry new policy versions.
- Actual pre-rental `ServerPickerModal` cards show community display reliability only at >=2 eligible sessions (including 0%), source/count/small-sample warning, original Vast provenance, observed jitter or N/A, review counts/ratings, and accessible comments icon that stops propagation. Original Vast filtering, sorting, recommendation score, and automatic selection are unchanged.
- Summary batches deduplicate machine IDs and cap each native request at 100. Summary counts and review pages are separately cached but both viewer/consent scoped, memory-only, bounded, and expire after 60 seconds. Consent/read failures/invalidation clear them and discard late responses. Reviews and eligibility are keyed during render as well as in effects, so a viewer change cannot briefly expose an earlier viewer’s page/prompt. Late moderation responses cannot fail a newer viewer’s reads. API failure restores Vast/N/A and leaves rental actions usable.
- Machine reviews show plain text, rating-only entries, coarse publication date/hardware, viewer-visible aggregates, bounded 20-item cursor pagination (deduplicated and guarded against repeated cursors), report and confirmed block controls. Blocks do not hide shared valid setup/jitter history. No contributor/session/rental ID is rendered in a review. Known empty comments are labeled `N/A · 0 comments`, distinct from unavailable reads; measured 0 ms jitter remains a real value. Dialog focus trapping/restoration, wrapping controls and card details, and adaptive rating columns support narrow screens.
- Existing destroy confirmation is extended with optional feedback only after native local eligibility confirms a tracked rental and actual frame evidence. No pairing/connection inference. Score starts unselected (1–10), comment <=2000 characters. Submit stages locally before the existing backup/destroy action; Skip stages both nulls, which the inspected desktop native service defines as a revisioned review tombstone, so a prior draft from a failed destruction cannot publish accidentally. Cancel before starting stages nothing and destroys nothing; cancellation after a failed destruction does not retract an earlier saved draft. Persistence errors/timeouts display a nonblocking warning and do not stop destruction. Native alone publishes after confirmed deletion and retains drafts across failed destruction.

## Native seam and runtime follow-up

- **Policy renewal limitation:** `feedback_program_consent` carries only `enabled` and `optionalContextEnabled`, not newly accepted policy versions. Rejoin is safely disabled if the published versions differ from saved versions; renewing changed versions requires a future coordinated native/API seam. The frontend does not silently accept new terms or invent an alternate command.
- **Skip semantics:** current desktop native source accepts `feedback_stage_review` with `score: null, comment: null` as a durable revisioned tombstone. Keep this behavior so Skip after a failed destroy cannot publish a prior draft. This is local staging only, not an empty review HTTP PUT.
- Real Tauri command registration, protected storage, frame-evidence eligibility, local staging durability, offline stop/delete synchronization, and native-only publication after provider deletion still need integration/runtime validation without prohibited native compilation in this implementation run.
- Published operator policies/contact and a valid public `NOLAND_FEEDBACK_API_URL` remain release configuration requirements. No production URL/contact is guessed. No Windows/Linux or real-device support is claimed from these frontend tests.

Suggested runtime checks when an already-built development app and configured test service are available: open/cancel enrollment while off (no registration), enroll without optional context, view unknown/one-outcome/two-failure machines, load/report/block paginated plain-text reviews, stop/delete offline and inspect pending status, and exercise Submit/Skip/Cancel plus staging/backup/provider-delete failures on test fixtures. Verify keyboard focus and wrapping at narrow window widths. Do not perform paid operations or send real contributions merely to validate this UI.
